# Plan 4a-2 — Kanji Reference (N4) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Extend the kanji reference with N4 — 177 hand-authored N4 kanji entries — and close three deferred findings from Plan 4a-1's final review that only became relevant once a second level's data exists: a single-codepoint guard in `validateKanji`, a level badge on cross-level search results, and a test that actually exercises Cyrillic case-folding.

**Architecture:** The Plan 4a-1 pipeline (`scripts/build-content/kanji.ts`) already merges every `*.tsv` file in `content/kanji/` into `kanji_points`, deriving the level from the filename — **no pipeline code changes are needed** to add a second level. This plan is almost entirely content authoring plus test extension, with three small, targeted code changes carried over from Plan 4a-1's final-review backlog.

**Tech Stack:** Unchanged from Plan 4a-1 — TypeScript, `sql.js`, React 18, react-router-dom, Vitest, Playwright. No new dependency.

**Spec:** `docs/superpowers/specs/2026-09-04-plan-4a-kanji-vocab-content-design.md` (same spec Plan 4a-1 argued from; this plan follows the same documented mechanism — hand-authored TSV, not scripted KANJIDIC2 import — for the same reason: 177 characters doesn't justify a network dependency).

**Predecessor:** `docs/superpowers/plans/2026-09-04-plan-4a-1-kanji-n5.md` (merged, commit `d2eedf8`). Read its Global Constraints — they still apply verbatim here except where this plan explicitly extends them.

**Carried over from Plan 4a-1's final review (opus), verbatim from the ledger:**
1. *Minor #1:* `KanjiListScreen`'s search results show no level indicator, unlike `GrammarListScreen` (which renders `{query ? <LevelBadge level={p.level} /> : null}`). Dormant while only N5 existed; live now that a cross-level search can return N4 hits mixed with N5 hits. → **Task 4**.
2. *Minor #2:* `validateKanji` doesn't check that `char` is exactly one codepoint — a hand-authoring typo (e.g. pasting two characters into one field) would silently produce a broken id. Recommended fix: `if ([...p.char].length !== 1) errors.push(...)` (spread, not `.length`, to count codepoints not UTF-16 units). → **Task 1** (done first, so Task 2's real data is validated by the stricter check from the start).
3. *Minor #5:* no test exercises actual Cyrillic case-folding (an uppercase query) — the code is correct, only the assertion was missing. → **Task 3**.

## Global Constraints

(Everything in Plan 4a-1's Global Constraints applies unchanged: browser-safe `src/**`, offline/deterministic `content.db` build, TSV format — 5 tab-separated fields, real TABs — `kanji_points.id` format, TDD, commit format, Node-not-on-PATH prefix. Restated here only what's new or level-status-specific:)

- **`content/kanji/n4.tsv` scope is 177 characters, not the ~179 a Wikibooks page's own prose claims.** The source page (`en.wikibooks.org/wiki/JLPT_Guide/JLPT_N4_Kanji`, CC BY-SA 3.0) states "179 kanji" in its text, but its own table lists 177 distinct characters — confirmed by two independent, differently-worded fetches of the live page returning byte-identical lists. This mirrors Plan 4a-1's N5 list, which had the same kind of self-inconsistency (page text said more than the table delivered). Treat 177 as the verified, actual scope; note the discrepancy in `CREDITS.md`, do not try to guess the 2 missing characters.
- **`levels.yml`'s N4 `status` stays `coming_soon`. Do NOT flip it to `available` in this plan.** The original master spec's per-category unlock model ties a level's availability to ALL of its categories (grammar + kanji + vocab) being ready, not just one. N4 grammar and N4 vocab don't exist yet (separate future plans). Flipping the status now would make `KanjiListScreen`'s N4 tab show the kanji grid while `GrammarListScreen`'s N4 tab still shows an empty "Ничего не найдено" — a confusing half-ready state. **This means the 177 real N4 rows land in `content.db` and are reachable via `ContentDb.listKanji('N4')`/`getKanji`/`searchKanji`, but `KanjiListScreen`'s N4 tab continues to show "Материал уровня N4 появится скоро." until whichever future plan completes N4 across all three categories and flips the status.** This is intentional — verify it, don't "fix" it.
- **Baseline: Vitest 149, Playwright e2e 14** (Plan 4a-1's final state) — no regressions.
