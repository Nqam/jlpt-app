## 1. Цель и рамки

### Цель

Довести контент N5+N4 до полноты: грамматика — до канонического списка (сейчас 8 из ~40+ пунктов
N5, N4 отсутствует вовсе), плюс новые категории кандзи и слов как справочник и материал для
будущих типов вопросов (план 4b). После плана 4a пайплайн `scripts/build-content/` производит
`content.db` с тремя полными категориями за N5+N4, и в приложении есть справочные экраны
«Кандзи» и «Слова» (сейчас — заглушки).

### В рамках плана 4a

- Источник охвата (какие именно пункты/кандзи/слова входят в N5 и N4) и источник черновых данных
  (чтения, значения, примеры) — открытые лицензии (§2).
- Грамматика: дописать прозу (Кратко/Образование/Нюансы/Примеры/Частые ошибки, формат плана 1)
  для всех пунктов N5+N4 из выбранного канонического списка. Уровень N4 переводится из
  `coming_soon` в `available` в `levels.yml`.
- Кандзи: новая категория контента. Чтения он/кун, значения (русский), кол-во черт, список слов
  уровня, где кандзи встречается. **Без порядка черт/анимации написания** — только для визуального
  узнавания (осознанное решение, не задел на будущее в рамках 4a).
- Слова: новая категория контента. Чтение (кана), значение (русский), часть речи, 1–3
  примера-предложения с фуриганой, список кандзи, входящих в слово (для будущего вопроса
  «кандзи↔слово», план 4b).
- Схема `content.db`: таблицы `kanji_points`, `vocab_points`, `vocab_kanji` (junction) — расширение
  `scripts/build-content/schema.sql`, аналогично `grammar_points`/`grammar_examples`.
- Справочные экраны «Кандзи» и «Слова» (список/поиск/карточка), по образцу
  `GrammarListScreen`/`GrammarDetailScreen` плана 1. Заменяют `PlaceholderScreen` на `/kanji` и
  `/vocab`.
- Пайплайн импорта из словарных дампов (KANJIDIC2, JMdict) с фильтром по каноническому списку —
  скриптовый, не ручное авторство по каждой единице.

### Вне рамок плана 4a (планы 4b–4d, 5)

- Типы вопросов кандзи/слово (`кандзи → слово`, `слово → кандзи`, ввод чтения каной) и включение
  кандзи/слов в `core/session.buildDailySession` — план 4b. Карточки кандзи/слов в `user.db`
  (`item_type = 'kanji' | 'vocab'`) заводятся только когда 4b даёт способ их повторять; в 4a
  контент читается исключительно справочными экранами, FSRS не касается.
- Раздел «Тексты», экран настроек — план 4c.
- Android/Capacitor — план 4d.
- Порядок черт кандзи, анимация написания, drawing-практика — сознательно исключено, не только
  отложено; если понадобится позже, это отдельный дизайн (новый источник данных — KanjiVG,
  новый тип рендеринга).
- Аудио, TTS — план 5.
- N3–N1 контент — контент есть в модели (`levels.yml` их уже перечисляет как `coming_soon`),
  наполнение — отдельные будущие планы.

### Поставка после плана 4a

`content.db` содержит полную грамматику N5+N4 (канонический список), справочники кандзи и слов
N5+N4 с открытыми данными и русским переводом. Приложение показывает три работающих справочных
раздела вместо одного. Материал готов для плана 4b (типов вопросов и SRS-карточек).

## 3. Архитектура

### Принципы (как в планах 1–3)

`src/core/**` и `src/storage/**` — чистый браузеро-совместимый TypeScript. `scripts/build-content/**`
— Node-код, вне ESLint-запрета на Node-импорты (как и раньше). `content.db` — детерминированная
сборка из версионируемых входов; сырые словарные дампы (JMdict/KANJIDIC2 XML, десятки МБ) НЕ
хранятся в git — кэшируются локально скриптом-загрузчиком, `build-content` явно падает с
понятной ошибкой, если дампов нет.

## 4. Схема данных

```sql
CREATE TABLE kanji_points (
  id            TEXT PRIMARY KEY,   -- напр. "n5-学"
  level         TEXT NOT NULL REFERENCES levels(code),
  char          TEXT NOT NULL,      -- сам иероглиф
  onyomi_json   TEXT NOT NULL,      -- ["ガク"]
  kunyomi_json  TEXT NOT NULL,      -- ["まな.ぶ"]
  meaning_ru    TEXT NOT NULL,      -- "учиться"
  stroke_count  INTEGER NOT NULL
);
CREATE INDEX idx_kanji_level ON kanji_points(level);

CREATE TABLE vocab_points (
  id           TEXT PRIMARY KEY,    -- напр. "n5-学校"
  level        TEXT NOT NULL REFERENCES levels(code),
  headword     TEXT NOT NULL,       -- 学校
  reading      TEXT NOT NULL,       -- がっこう
  pos          TEXT NOT NULL,       -- часть речи, краткий код JMdict (n, v1, adj-i, ...)
  meaning_ru   TEXT NOT NULL
);
CREATE INDEX idx_vocab_level ON vocab_points(level);

CREATE TABLE vocab_examples (
  vocab_id TEXT NOT NULL REFERENCES vocab_points(id),
  ord      INTEGER NOT NULL,
  ja_ruby  TEXT NOT NULL,
  ru       TEXT NOT NULL,
  PRIMARY KEY (vocab_id, ord)
);

CREATE TABLE vocab_kanji (
  vocab_id TEXT NOT NULL REFERENCES vocab_points(id),
  kanji_id TEXT NOT NULL REFERENCES kanji_points(id),
  PRIMARY KEY (vocab_id, kanji_id)
);
```

Формат `id` (`{level}-{значимая часть}`) и наличие `tags_json`-подобных полей — по образцу
`grammar_points`, для единообразия читаемости дампов при отладке. `onyomi_json`/`kunyomi_json` —
JSON-массивы строк (как `tags_json` у грамматики), а не отдельные таблицы: списки коротки (обычно
1–4 чтения), отдельная таблица была бы оверинжинирингом на уровне плана 1's `tags_json` решения.

## 5. Пайплайн импорта

1. `npm run fetch-dictionaries` (новый скрипт, отдельный от `build-content` — сеть нужна только
   один раз/по требованию, `build-content` остаётся офлайн-детерминированным при наличии кэша).
   Скачивает `JMdict_e.gz` и `kanjidic2.xml.gz` с EDRDG-зеркал, распаковывает в
   `.cache/dictionaries/` (в `.gitignore`).
2. `npm run build-content` (существующий, расширенный):
   - Как раньше: парсит `content/grammar/**/*.md` → `grammar_points`/`grammar_examples`/`grammar_relations`.
   - Новое: читает `content/kanji/{level}.txt` (один символ на строку), для каждого ищет запись в
     `.cache/dictionaries/kanjidic2.xml`, извлекает чтения/значения/черты, переводит значение на
     русский (**вручную курируемый файл** `content/kanji/meanings-ru.tsv`: символ→русский перевод,
     т.к. KANJIDIC2 даёт только английские глоссы — автоматический перевод не отвечает планке
     качества плана 1's переводов).
   - Читает `content/vocab/{level}.tsv` (заголовок⇥чтение, чтение снимает омографию), ищет в JMdict
     по заголовку+чтению, извлекает часть речи + английские значения → аналогичный курируемый файл
     `content/vocab/meanings-ru.tsv` для русского перевода; примеры — сперва пробует точное
     совпадение заголовка в локальном срезе Tatoeba (файл, не полный корпус — фильтр по
     японский+русский пары, если такая пара существует в Tatoeba; иначе секция примеров пуста,
     тест это допускает, не требует).
   - Валидатор (расширение существующего валидатора грамматики плана 1): каждый `kanji_points`/
     `vocab_points` имеет непустые обязательные поля; каждый `vocab_kanji` ссылается на кандзи,
     реально присутствующий в `kanji_points` того же или более раннего уровня (слово N4 может
     использовать кандзи N5, не наоборот — валидатор это проверяет, ловит нарушения).
3. Собранный `content.db` — как раньше, детерминирован при фиксированных входных файлах +
   зафиксированной версии словарных дампов (версия дампа — поле в `meta`, как `content_version`).

## 6. UI

### `KanjiListScreen` / `KanjiDetailScreen`

По образцу грамматики: список по уровню, поиск (по символу или значению — JS-фильтр, как
`searchGrammar`, объём тот же порядок величины). Карточка: символ крупно, чтения (он/кун отдельными
строками), значение, кол-во черт, список слов уровня, где встречается (ссылки на `VocabDetailScreen`
через `vocab_kanji`).

### `VocabListScreen` / `VocabDetailScreen`

Список по уровню, поиск по заголовку/чтению/значению. Карточка: заголовок с фуриганой (через
`Furigana`, `headword[reading]` synth-строка), часть речи, значение, примеры (через `Furigana`, как
у грамматики), кандзи слова — кликабельные бейджи на `KanjiDetailScreen`.

### Навигация

`Nav.tsx` уже содержит пункты «Кандзи»/«Слова» (ведут на `PlaceholderScreen` — плейсхолдер меняется
на реальные экраны, сам `Nav` не трогается).

## 7. Открытые вопросы

- **Точность списка кандзи N5.** Найденный список Wikibooks (§2) в одном из источников отмечен как
  неполный (80 из ныне принятых ~103 символов). При реализации: взять легаси-поле `jlpt` в
  KANJIDIC2 (старая 4-уровневая шкала: уровень 4 ≈ текущий N5, уровень 3 ≈ текущий N4) как второй
  источник, объединить множества, разницу разрешить вручную (список невелик, ручная сверка дешевле
  третьего источника). Не блокирует дизайн — процедурный шаг плана реализации.
- **Русские переводы значений** курируются вручную (`meanings-ru.tsv`) — открытый вопрос объёма:
  сколько времени займёт перевод ~103+179 кандзи + ~800+ слов. Решение по факту: если объём
  окажется непосильным для одной сессии реализации, план 4a можно дополнительно разбить на
  4a-kanji и 4a-vocab (или сократить охват N4 до кандзи+грамматики, слова N4 — в follow-up) —
  ревью реализации примет решение по факту трудозатрат, не блокирует написание плана.
- **Строгость валидатора `vocab_kanji`** (слово не может использовать кандзи выше своего уровня)
  — учебные списки Wikibooks/JMdict не гарантируют это на 100%; при реализации решить: жёсткая
  ошибка сборки или предупреждение в лог (вероятнее — предупреждение, т.к. блокировать сборку из-за
  контентных нюансов методологии составителей списков избыточно).
