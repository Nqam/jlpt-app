# Дизайн: план 4e — вступительный тест (placement)

## 1. Контекст и цель

Дизайн-спека `2026-09-03-jlpt-desktop-app-design.md` описывает модуль `placement`
(§3, таблица модулей) и экран «Вступительный тест» (§7, экран 9): адаптивный тест на
первом запуске (и повторно из настроек), который определяет, что пользователь уже
знает, и сразу проставляет начальные статусы — чтобы не заставлять того, кто уже
что-то знает, проходить весь N5 с нуля.

Сейчас модуля `placement` нет вообще — ни маршрута, ни ядра, ни экрана. Это первый
самостоятельный план после закрытия 4a/4b/4c-1 (нумерация «4e», т.к. «4c»/«4d» уже
заняты Текстами и Android соответственно в изначальной декомпозиции — см. память
проекта; порядок реализации по факту: 4e раньше 4c-2/4d, т.к. пользователь так решил).

## 2. Объём

**Только грамматика.** Кандзи и слова не участвуют в тесте (явное решение
пользователя) — их начальный статус остаётся как сейчас (первая карточка уровня
предлагается на общих основаниях через `scheduler.ts`).

**Результат — сразу SRS-карточки в статусе «знаю».** Не сдвиг курсора очереди, а
реальные записи в `cards`: для каждого пункта грамматики, определённого тестом как
«уже известный», создаётся карточка через ОДИН симулированный проход с оценкой
«Хорошо» (`review(newCard(...), 3, now, 0, params)`, реальный FSRS-движок, не
выдуманные числа) — карточка получает нормальный due по FSRS, дальше живёт в обычном
цикле повторений. **В `review_log` ничего не пишется** — это не настоящая учебная
сессия, не должна раздувать «стрик»/счётчик повторений за день.

**Повторный запуск (из настроек) не трогает существующий прогресс.** Тест создаёт
карточки ТОЛЬКО для пунктов, у которых карточки ещё нет вообще (`user.getCard(...) ===
null`) — никогда не откатывает и не перезаписывает то, что пользователь уже реально
изучал/повторял. Список кандидатов для теста поэтому — это все доступные (`available`)
пункты грамматики, без исключения уже прогрессирующих (см. §3 — тест сам проверяет
существование карточки только на этапе применения результата, не на этапе выбора
вопросов, чтобы порядок вопросов оставался детерминированным независимо от того, что
уже отслеживается).

## 3. Алгоритм — бинарный поиск

Список кандидатов — уже существующий канонический порядок
`availableItemIds(content, 'grammar')` из `scheduler.ts` (level.ord → layer → id),
**переиспользуется, не дублируется** (функция становится `export`, была приватной).

Инвариант: `lo`/`hi` — границы диапазона, где проходит граница «знает/не знает» среди
`ids`; `ids[0, lo)` подтверждено известно, `ids[hi, length)` подтверждено неизвестно.
Каждый шаг спрашивает `ids[floor((lo+hi)/2)]`: верно → `lo = idx+1`; неверно →
`hi = idx`. Тест завершён, когда `lo >= hi`; граница = `lo`.

- Все ответы верны → `lo` доходит до конца списка → известно всё (верхняя оценка).
- Все ответы неверны → `hi` схлопывается к 0 за пару шагов → известно ничего
  (эквивалентно пропуску теста).
- Смешанные ответы → граница сходится где-то в середине — именно так, как описывают
  собственные приёмочные тесты модуля в главной дизайн-спеке
  («адаптивный тест сходится; все верны — верхняя оценка; смешанные — средняя»).

**Отклонение от «~15-20 вопросов» из главной спеки, зафиксировано осознанно:** чистый
бинарный поиск сходится за `⌈log₂(N+1)⌉` вопросов — для нынешних ~93 пунктов N5+N4 это
≤7 вопросов, не 15-20. Число «15-20» в исходной спеке было ориентировочным для гораздо
большего корпуса (когда появятся N3-N1). Пришлось выбирать между (a) честным коротким
тестом, который **доказуемо сходится и не угадывает**, и (b) искусственным раздуванием
числа вопросов ради соответствия цифре из ранней прикидки. Выбран (a) — раздувание
вопросами, не несущими дополнительной информации, было бы обманом пользователя
(«тест длиннее, чем нужно для ответа»), а число вопросов и так растёт вместе с
контентом автоматически. Число вопросов НЕ хардкодится нигде — оно следствие текущего
размера `availableItemIds(content, 'grammar')`.

**Генерация вопросов** — переиспользуется существующий `generateForCard` (тот же,
что использует обычная сессия повторения) с `reps=0`: у грамматики уже есть полный
реестр типов вопросов (cloze/choice/assemble) с фолбэк-цепочкой, ничего нового не
нужно писать.

## 4. Экраны

**Предложение при первом запуске** — не отдельный роут, а условная ветка в
`TodayScreen.tsx`: если у пользователя вообще нет ни одной карточки грамматики
(`user.allCards('grammar').length === 0`) И флаг `placement_offered` (новый ключ
`settings`, дефолт `false`) не установлен — вместо обычного контента «Сегодня»
показывается «Хотите пройти вступительный тест?» с кнопками «Пройти» (→ `/placement`)
и «Пропустить» (ставит `placement_offered = true`, показывает обычный «Сегодня»).
После первого решения (в любую сторону) предложение больше никогда не всплывает само.

**Экран теста** — новый роут `/placement`, `PlacementScreen.tsx`. Один вопрос за раз
через уже существующий `QuestionView`/`grade()` — тот же паттерн, что `ReviewScreen`.
По завершении — экран с итогом («Готово. Отмечено N пунктов как уже известные») и
кнопкой на «Сегодня».

**Повторный запуск из настроек** — обычная ссылка «Пройти вступительный тест заново»
в `SettingsScreen.tsx`, ведёт на `/placement`. Не трогает `placement_offered` (флаг
только про автопоказ на первом запуске).

## 5. Тестирование

- Unit: `src/core/placement.ts` — сходимость при всех верных/всех неверных/смешанных
  ответах (с ручным трейсом на маленьком списке), верхняя граница числа вопросов
  (`⌈log₂(N+1)⌉`), `nextPlacementQuestion` возвращает `null` после завершения,
  генерируемый вопрос — реальный `generateForCard`-результат (`itemType: 'grammar'`).
- Unit: `PlacementScreen.tsx` — полный прогон на маленьком фейковом наборе пунктов,
  проверка что `upsertCard` вызван для нужных id и НЕ вызван `insertReviewLog`.
- Unit: `TodayScreen.tsx` — новая ветка предложения показывается/не показывается по
  условию, «Пропустить» вызывает `setSetting('placement_offered', true)`.
- Unit: `SettingsScreen.tsx` — новая ссылка на `/placement` присутствует.
- e2e: полный прогон на реальном Electron — свежий `user.db` → видно предложение →
  прошёл тест (отвечая одинаково на все вопросы, чтобы результат был детерминирован
  границей 0 или "всё") → карточки появились в `cards` с нужным `item_type`.

## 6. Не в объёме этого плана

- Кандзи/слова в тесте — не участвуют.
- Автозапуск теста при апдейте контента (новые уровни) — не предусмотрен, тест
  запускается только вручную из настроек или один раз на первом старте.
- Изменение уже существующих карточек повторным запуском теста — явно исключено.
