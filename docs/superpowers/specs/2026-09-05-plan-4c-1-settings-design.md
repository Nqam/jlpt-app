# Дизайн: план 4c-1 — экран «Настройки»

## 1. Контекст и цель

Дизайн-спека `2026-09-03-jlpt-desktop-app-design.md` §10 описывает экран «Настройки»:
дневные нормы нового материала, предел повторений, звук, тема, фуригана вкл/выкл,
экспорт/импорт `user.db`. Сейчас `/settings` — `PlaceholderScreen`, реального экрана
нет. Существующие настройки (`new_per_day`, `review_queue_cap`, `fsrs_*`) читаются в
коде (`scheduler.ts`, `ReviewScreen.tsx`) с дефолтами, но менять их пользователю
негде — их можно только руками прописать в `user.db`.

План 4 (§ решённое в этой сессии) разбит на 4c-1 (этот план, Настройки) и 4c-2
(Тексты) — независимые подсистемы, отдельные план-документы, как было с 4a/4b.

**Пункт «звук»/TTS исключён из объёма по явному решению пользователя** (озвучки по
Web Speech API нет в коде вообще, и пользователь передумал её реализовывать —
ни настройка, ни функциональность в этот план не входят).

**Тема (`ThemeToggle`) не трогается** — остаётся отдельной кнопкой в навбаре, экран
Настроек её не дублирует (явное решение пользователя, риск рассинхронизации двух
переключателей одного состояния перевешивает выгоду).

## 2. Экран «Настройки»

Путь `/settings`, заменяет `PlaceholderScreen`. Три поля + блок резервной копии:

1. **«Новых карточек в день»** — число, ключ `new_per_day` (дефолт 5, как сейчас в
   `scheduler.ts:28`). Валидация: целое ≥ 1.
2. **«Предел повторений в очереди»** — число, ключ `review_queue_cap` (дефолт 100, как
   сейчас в `scheduler.ts:29`). Валидация: целое ≥ 1.
3. **«Показывать фуригану»** — тумблер, новый ключ `furigana_enabled` (дефолт `true`).
4. **«Резервная копия»** — кнопки «Экспортировать» и «Импортировать» (см. §4).

FSRS-параметры (`fsrs_request_retention`, `fsrs_maximum_interval`, `fsrs_enable_fuzz`)
**не выносятся в UI** — внутренняя тонкая настройка, спека §10 их не упоминает как
пользовательские, остаются как есть (дефолты в `ReviewScreen.tsx`).

Изменение поля сразу пишет через `user.setSetting(key, value)` — без отдельной кнопки
«Сохранить» (как остальной проект: SRS-параметры и тема применяются немедленно, без
промежуточного состояния «черновик»).

## 3. Фуригана: чтение настройки

`src/ui/components/Furigana.tsx` уже принимает `showFurigana` (проп, дефолт `true`,
сейчас ни один из ~5 вызовов его не передаёт — мёртвый параметр). Меняем дефолт:
компонент читает `user.getSetting('furigana_enabled', true)` через `useUserDb()` и
использует это значение, если `showFurigana` не передан явно вызывающим кодом. Явный
проп (если когда-нибудь понадобится) продолжает иметь приоритет. Ни один существующий
вызов компонента не меняется.

## 4. Экспорт/импорт `user.db`

**Только ручной, по кнопке.** Автоэкспорт раз/неделю (упомянут в дизайн-спеке §"Android")
исключён из объёма по решению пользователя — отдельный follow-up, если понадобится.

Новые методы `PlatformAdapter` (десктоп-реализация через Electron `dialog`+`fs` по IPC,
Android — не реализуется в этом плане, `throw`/`unsupported` как в существующих
desktop-only методах, если такие есть — проверить паттерн в `desktop.ts` перед
реализацией):

```ts
/** Диалог "Сохранить как", пишет байты по выбранному пути. `false`, если отменено. */
exportUserDb(bytes: Uint8Array): Promise<boolean>;
/** Диалог "Открыть", читает выбранный файл. `null`, если отменено. */
importUserDb(): Promise<Uint8Array | null>;
```

**Экспорт:** текущие байты `user.db` (через `UserDb`'s already-available serialize/get
raw bytes path — проверить точный метод в `user-db.ts` при реализации) → `exportUserDb`.
Предложенное имя файла по умолчанию: `jlpt-backup-YYYY-MM-DD.db`.

**Импорт:** подтверждение («это заменит весь текущий прогресс, продолжить?») → байты
через `importUserDb` → валидация (открыть sql.js на байтах, проверить наличие таблиц
`cards`/`review_log`/`settings`/`meta` из `migrations.ts`'s `V1_SCHEMA` — самая дешёвая
проверка «это вообще наш user.db», без полного прогона `applyMigrations`) → при успехе
записать как `user.db` через существующий `adapter.writeUserDb` → `window.location.reload()`
(перезагружает рендерер тем же Electron-окном; main-процесс и его хендлеры close/flush не
трогаются — простая и надёжная переинициализация состояния вместо ручной инвалидации
живого React-дерева или новой relaunch-IPC). При ошибке валидации — сообщение об ошибке,
ничего не перезаписывается.

## 5. Тестирование

- Unit: `SettingsScreen` — рендер текущих значений, изменение поля → `setSetting`
  вызван с ожидаемым ключом/значением, кнопки экспорта/импорта вызывают
  `adapter.exportUserDb`/`importUserDb` (мок), сообщение об ошибке при неверном файле
  импорта, диалог подтверждения перед импортом.
- Unit: `Furigana` — новый тест на дефолт из `furigana_enabled=false`.
- Unit/integration: новые методы `PlatformAdapter` в desktop-реализации (мок Electron
  `dialog`/`fs`).
- **Решено:** `exportUserDb`/`importUserDb` — обязательные методы `PlatformAdapter`
  (согласуется с паттерном плана 4b, где новый `ItemType`-член аналогично требовал
  правки всех фейков одним проходом; опциональные методы позволили бы забыть
  Android-реализацию без ошибки компиляции). Эмпирически проверено (`tsc --noEmit`
  после пробного добавления обоих методов как required): ломаются ровно 6 мест —
  `src/platform/desktop.ts` (реальная реализация) и 5 файлов с `fakeAdapter`/
  `fakeAdapter: PlatformAdapter` (`tests/core/scheduler.test.ts`,
  `tests/core/session.test.ts`, `tests/core/progress.test.ts`,
  `tests/storage/user-db.test.ts`, `tests/storage/content-db.test.ts`) — план должен
  добавить обе заглушки (`async exportUserDb() { throw new Error('unused'); }` и
  аналогично `importUserDb`, в духе уже существующего `readBundledContentDb` в тех же
  фейках) во все пять тестовых файлов одним batched-проходом (одна задача, не пять).
- e2e: изменение настройки (`new_per_day`/`review_queue_cap`/`furigana_enabled`)
  персистится между перезапусками (как `kanji-review.spec.ts` паттерн: закрыть/открыть
  заново, прочитать `user.db`). Экспорт/импорт через реальный OS-диалог не тестируем в
  e2e (Playwright не может надёжно управлять нативным диалогом Electron, и debug-hook
  ради этого не заводим — решено пользователем) — покрываем только unit-уровнем с
  мок-адаптером.

## 6. Не в объёме этого плана

- Звук/TTS (озвучка) — исключено по решению пользователя.
- Тема в экране Настроек — остаётся в навбаре, не дублируется.
- FSRS advanced-параметры в UI.
- Автоэкспорт по расписанию.
- Android-реализация `exportUserDb`/`importUserDb` (план 4d).
- План 4c-2 (Тексты) — отдельный план, отдельная сессия.
